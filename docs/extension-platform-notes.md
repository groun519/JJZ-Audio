# 확장 기능 플랫폼 설계 메모

## 문서 상태

- 상태: 보류
- 기록일: 2026-08-19
- 목적: JJZero Audio의 실험적·선택적 기능을 메인 제품과 분리하고, 향후 제3자 확장 생태계로 발전시킬 수 있는 기준을 보존한다.
- 첫 검증 후보: RVC 보이스 신디사이저

이 문서는 구현 계획이나 출시 약속이 아니다. 확장 기능을 실제로 착수할 때
호환성과 보안을 뒤늦게 다시 설계하지 않도록 현재 합의한 방향만 기록한다.

## 도입 이유

- RVC 보이스 신디사이저처럼 일부 사용자만 필요로 하는 기능을 메인 화면과 설치 용량에 강제로 포함하지 않는다.
- 추가 분리 모델, 고급 편집 도구, 외부 서비스 연동처럼 서로 다른 기능을 독립적으로 설치·제거할 수 있게 한다.
- 공식 기능으로 시작하더라도 제3자 제작자가 같은 구조를 사용할 수 있게 한다.
- 확장 하나의 오류나 중단이 메인 앱, 재생, 라이브러리를 종료시키지 않게 한다.

## 확정 방향

1. 사용자 명칭은 `확장 기능`으로 통일한다.
2. 처음부터 제3자 코드를 가정하지만 초기 공개 범위는 공식 확장으로 제한할 수 있다.
3. 앱 버전과 별도로 `Extension API` 버전을 두고 호환성을 판단한다.
4. 확장 Python 코드는 메인 프로세스에서 직접 import하지 않고 별도 프로세스에서 실행한다.
5. 파일, 네트워크, GPU, 외부 프로세스 실행 권한은 설치 전에 명시하고 사용자 동의를 받는다.
6. 확장 데이터, 모델, 캐시와 설정은 확장 ID별로 격리한다.
7. 확장 제거 시 생성한 사용자 결과물과 다시 받을 수 있는 캐시를 구분한다.
8. 공식, 검증된 커뮤니티, 미확인 확장을 UI에서 명확히 구분한다.

## 패키지 초안

확장 패키지 확장자는 `.jjzext`를 우선 후보로 둔다.

```text
example.jjzext
├─ manifest.json       확장 ID, 버전, API 호환 범위, 권한, 제작자
├─ backend/            별도 프로세스에서 실행할 처리 로직
├─ ui/                 앱이 렌더링할 선언형 페이지와 패널 정의
├─ resources/          아이콘과 번역
├─ migrations/         확장 데이터 스키마 이전
└─ runtime/            선택적 추가 의존성 정보
```

초기 Extension API 후보는 다음과 같다.

- `AudioProcessor`: 오디오 입력을 처리해 결과를 생성한다.
- `ModelProvider`: 확장 모델을 탐색하고 제공한다.
- `JobProvider`: 작업 대기열에 장시간 작업을 등록한다.
- `PageContribution`: 독립 페이지를 등록한다.
- `PanelContribution`: 기존 페이지의 허용된 위치에 패널을 등록한다.
- `CommandContribution`: 명령, 버튼과 단축키를 등록한다.
- `LibraryProvider`: 결과물을 JJZero Audio 라이브러리에 등록한다.

## 사용자 설치 경로

세 가지 설치 경로가 같은 검증·설치 파이프라인을 사용해야 한다.

1. 앱 내 확장 기능 화면에서 조회하고 설치한다.
2. 공유받은 확장 링크를 앱에서 연다.
3. 로컬 `.jjzext` 파일을 드래그하거나 선택해 설치한다.

앱 내 화면에서는 이름, 제작자, 버전, 설명, 이미지, 다운로드·설치 용량,
지원 앱/API 버전, GPU·런타임 요구사항, 권한, 서명과 검증 상태를 표시한다.

```text
다운로드
-> 패키지 해시와 제작자 서명 확인
-> 임시 영역에서 구조와 권한 검증
-> 기존 버전 복구 지점 생성
-> 새 버전 활성화
-> 실패 시 이전 버전 자동 복구
```

## 제작자 배포 흐름

```text
Extension SDK로 제작
-> 개발자 모드에서 로컬 테스트
-> .jjzext 빌드
-> 자동 정적·구조 검증
-> 제작자 서명
-> 카탈로그 등록 요청
-> 검토 후 앱 내 노출
```

확장 ID와 제작자 서명 키의 관계는 첫 공개 후 임의로 바꿀 수 없게 한다.
업데이트는 동일 제작자의 유효한 서명과 허용된 버전 상승일 때만 설치한다.

## 비용 없는 초기 운영안

초기 카탈로그와 패키지는 공개 GitHub 인프라를 사용한다.

```text
JJZero Audio 공개 카탈로그 저장소
├─ catalog.json
├─ publishers.json
└─ 확장별 메타데이터

각 제작자의 GitHub Release
└─ extension-name-version.jjzext
```

- 앱은 정적 카탈로그를 캐시해 확장 목록과 업데이트를 확인한다.
- 패키지는 각 제작자의 GitHub Release에서 직접 받는다.
- 카탈로그 등록 요청은 PR로 받고 공개 GitHub Actions에서 자동 검증한다.
- 중앙 서버와 데이터베이스를 직접 운영하지 않는 것을 초기 원칙으로 한다.
- GitHub 정책과 한도는 영구 보장되지 않으므로 저장소 공급자를 인터페이스로 분리한다.
- 향후 공급자가 바뀌어도 카탈로그, 검증, 설치 API는 유지한다.

- [GitHub REST API 요청 한도](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

## 구현 전에 결정할 항목

- 서명 방식과 신뢰할 제작자 등록·폐기 절차
- 확장 프로세스 통신 규격과 중단·시간 초과 정책
- 선언형 UI가 허용할 컴포넌트와 기존 페이지 삽입 위치
- 권한 종류와 Windows에서 실제로 강제할 수 있는 격리 범위
- Python 및 네이티브 의존성 충돌 방지 방식
- 유료 확장과 결제는 지원할지 여부
- 악성·방치된 확장의 신고, 차단과 카탈로그 제거 정책
- 카탈로그 장애 시 설치된 확장을 오프라인으로 계속 실행할 정책

## 범위 제외

- 메인 앱 폴더의 Python 파일을 그대로 불러오는 단순 `plugins` 폴더 방식
- 서명과 권한 확인 없이 링크를 바로 실행하는 방식
- 확장 캐시와 사용자 라이브러리를 함께 제거하는 방식
- 현재 단계에서 스토어 서버, 계정 시스템 또는 결제 시스템을 구현하는 일

## 재개 조건과 첫 단계

다음 중 하나가 실제 우선순위가 되었을 때 이 문서를 구현 계획으로 전환한다.

- RVC 보이스 신디사이저를 제품 실험 기능으로 만들기로 결정한다.
- 메인 설치에서 분리해야 할 대형 모델 또는 런타임이 두 개 이상 생긴다.
- 제3자 제작자가 확장을 제작·배포할 구체적인 수요가 생긴다.

재개 시 첫 마일스톤은 스토어 UI가 아니다. `manifest v1`, Extension API v1의
최소 계약, 별도 프로세스 호스트, 로컬 설치·비활성화·제거·복구를 먼저 만들고
RVC 보이스 신디사이저 공식 확장 하나로 구조를 검증한다.
