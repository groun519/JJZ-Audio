# JJZero Audio Update Center Design

## Summary

JJZero Audio의 업데이트를 단일 진행 막대가 있는 차단형 창에서 구성요소별 상태를 보여주는 업데이트 센터로 변경한다. 다운로드와 검증은 앱을 사용하는 동안 백그라운드에서 계속하고, 실행 중인 작업과 충돌하지 않는 구성요소만 앱 내부에서 적용한다. 앱 본체나 로드된 DLL처럼 안전한 교체에 재시작이 필요한 항목은 종료 시점으로 미룬다.

업데이트 센터는 단계와 용량을 명확하게 보여주되 패치노트를 내부에 복제하지 않는다. 하단의 `패치노트 보기 ↗` 링크가 해당 버전의 웹 릴리스 페이지를 기본 브라우저로 연다.

## Goals

- 현재 진행 단계, 구성요소, 다운로드 크기, 남은 작업을 사용자가 이해할 수 있게 한다.
- 시작된 다운로드와 검증은 업데이트 창을 닫아도 앱 내부에서 계속한다.
- 분리, 변환, 학습, 재생 작업을 중단하지 않고 적용 가능한 항목만 안전한 시점에 교체한다.
- 실패 시 현재 정상 버전을 유지하고 재시도할 수 있게 한다.
- 업데이트 전용 캐시를 성공 후 자동 정리하되 라이브러리와 사용자 데이터를 절대 건드리지 않는다.
- 패치노트를 업데이트 진행과 독립적으로 웹에서 읽을 수 있게 한다.

## Non-goals

- 실행 중인 Python 프로세스나 DLL을 강제로 교체하는 완전한 무중단 업데이트
- 라이브러리, 모델, 출력 파일, 설정, OAuth 데이터의 정리
- 일반 미디어 파형/썸네일 캐시의 전면 삭제
- 애플리케이션 내부 패치노트 편집기 또는 Markdown 렌더러
- 여러 앱 버전을 사용자가 임의로 선택하는 버전 관리자

## User Flow

### 1. Update available

1. 앱이 기존 방식대로 릴리스 매니페스트를 확인한다.
2. 업데이트가 있으면 전역 업데이트 상태 버튼을 표시한다.
3. 사용자가 버튼을 누르면 업데이트 센터가 열린다.
4. 센터는 전체 다운로드 크기, 설치 후 필요한 추가 공간, 구성요소와 재시작 필요 여부를 먼저 보여준다.
5. 다운로드는 사용자가 `업데이트 준비`를 눌렀을 때 시작한다. 수 GB 런타임을 예고 없이 내려받지 않는다.

### 2. Background preparation

1. 창을 닫거나 `백그라운드로 보내기`를 누르면 다운로드와 검증은 계속된다.
2. 전역 업데이트 상태 버튼은 진행률 또는 `준비됨` 상태를 보여준다.
3. 센터를 다시 열면 같은 작업 상태를 복원한다. 중복 작업을 만들지 않는다.
4. 네트워크 중단 시 `.part` 파일을 이용해 재개하고, 체크섬 또는 서명 검증 실패 시 해당 파일만 폐기한다.

### 3. Apply

1. 다운로드가 끝나면 구성요소별로 `적용 가능`, `작업 종료 대기`, `재시작 필요` 상태를 표시한다.
2. 런타임 적용은 RVC 변환, 분리, 학습 등 해당 런타임을 사용하는 작업이 없을 때만 시작한다.
3. 활성 작업이 있으면 강제 중단하지 않고 `현재 작업이 끝나면 적용` 상태로 대기한다.
4. 앱 본체와 로드된 DLL은 스테이징만 하고 `완료 후 재시작` 또는 다음 앱 종료 시 설치한다.
5. 런타임만 변경되는 업데이트는 검증과 활성화가 성공하면 재시작 없이 완료할 수 있다. 단, 이미 프로세스에 로드된 구성요소는 재시작 대상으로 승격한다.

### 4. Completion and cleanup

1. 새 구성요소의 구조 검증과 최소 실행 진단이 성공해야 설치 완료로 기록한다.
2. 앱 본체 업데이트는 새 버전 첫 정상 시작을 확인한 뒤 완료로 기록한다.
3. 완료 확인 후 업데이트 ZIP/EXE, 완료된 `.part`, 이전 런타임 백업을 정리한다.
4. 실패한 경우 현재 버전을 복원하거나 그대로 유지하고, 오류 요약과 진단 ID를 제공한다.

## Update Center UI

### Layout

기존 B안의 상세 업데이트 센터를 사용한다.

- 좌측 단계 목록: `다운로드`, `런타임 적용`, `앱 업데이트`, `정리 및 확인`
- 우측 현재 단계: 구성요소 이름, 상세 상태, 현재/전체 용량, 진행률, 예상 남은 시간
- 요약 정보: 다음 단계, 정리 예정 용량, 사용자 데이터 보호 상태
- 주요 동작: `백그라운드로 보내기`, `지금 적용`, `완료 후 재시작`, `다시 시도`
- 하단 보조 링크: `패치노트 보기 ↗`

단계는 `대기`, `진행 중`, `완료`, `확인 필요`, `실패`를 색상과 아이콘으로 구분한다. 아직 시작하지 않은 단계를 실패로 보이지 않게 한다.

### Release notes link

- `패치노트 보기 ↗`는 앱 내부 화면을 전환하지 않고 운영체제 기본 브라우저를 연다.
- 매니페스트에 선택적 `release_notes_url`을 추가하고 HTTPS URL만 허용한다.
- 필드가 없는 구형 매니페스트는 GitHub의 버전 태그 URL을 사용한다.
- 링크 열기 실패는 업데이트 자체의 실패로 처리하지 않고 짧은 토스트만 표시한다.

### Background behavior

- 업데이트 센터는 모달 설치 마법사가 아니라 닫았다 다시 열 수 있는 상태 뷰다.
- 백그라운드 상태는 기존 전역 업데이트 버튼을 재사용한다.
- 진행 중에는 `64%`, 준비 완료 후에는 `재시작 필요` 또는 `적용 가능`을 표시한다.
- 백그라운드 작업이 끝나면 Windows 작업 표시줄 알림과 앱 내부 토스트를 한 번만 발생시킨다.

## Architecture

### Update coordinator

UI와 설치 로직 사이에 단일 `UpdateCoordinator`를 둔다. 모든 업데이트 동작은 이 객체를 통해 수행하고, 창을 닫아도 객체와 작업은 메인 윈도우 수명 동안 유지한다.

상태는 다음 순서로 전이한다.

```text
AVAILABLE
  -> DOWNLOADING
  -> VERIFYING
  -> READY
  -> WAITING_FOR_IDLE | WAITING_FOR_RESTART
  -> APPLYING
  -> HEALTH_CHECK
  -> CLEANING
  -> COMPLETE
```

모든 진행 상태에서 `FAILED`로 이동할 수 있으며, 재시도 가능한 단계와 복구 동작을 함께 기록한다.

### Persistent journal

`settings/update-state.json`에 작은 업데이트 저널을 원자적으로 기록한다.

- 대상 앱 버전과 구성요소 버전
- 매니페스트 URL과 릴리스 노트 URL
- 아티팩트 이름, 크기, 체크섬, 다운로드 상태
- 현재 단계와 마지막 성공 단계
- 스테이징/백업 경로
- 재시작 필요 여부
- 실패 진단 ID와 마지막 오류 요약

앱 시작 시 저널을 읽어 다운로드 재개, 설치 완료 확인, 롤백 또는 안전한 정리를 결정한다. 파일 경로는 반드시 관리되는 업데이트 캐시와 런타임 루트 내부인지 재검증한다.

### Component safety

구성요소마다 적용 정책을 명시한다.

| Component | Background download | In-app apply | Restart |
| --- | --- | --- | --- |
| Application installer | Yes | Stage only | Required |
| Base AI runtime | Yes | Idle only | Conditional |
| RVC GPU profile | Yes | Idle only | Conditional |
| Separation model asset | Yes | When model is unused | No |
| Update metadata | Yes | Immediate | No |

`Idle only`은 관련 작업 큐가 비었고 해당 실행 프로세스가 종료된 상태를 뜻한다. UI 재생만 멈추는 것으로 런타임이 유휴 상태라고 판단하지 않는다.

## Cache and Rollback Policy

업데이트 파일은 일반 캐시와 섞지 않고 `Cache/updates/<version>/` 아래에 저장한다. 자동 정리는 이 루트와 관리되는 런타임의 명시적 스테이징 경로로 제한한다.

### Safe to remove automatically

- 성공적으로 설치된 업데이트 ZIP/EXE
- 체크섬이 틀린 다운로드와 재개 불가능한 `.part`
- 활성 저널이 참조하지 않는 오래된 버전의 업데이트 디렉터리
- 실패 후 남은 `.installing` 스테이징 디렉터리
- 새 버전 정상 실행 확인이 끝난 `.previous` 런타임 백업
- 패키지 내부 `__pycache__`와 소스맵처럼 실행에 필요 없는 생성물

### Never remove automatically

- `Data`, `workspace`, 라이브러리 카탈로그와 곡 디렉터리
- 모델 `.pth`, `.index`, 학습 재료와 체크포인트
- `Output`과 사용자가 내보낸 결과물
- 설정, 저장 위치, OAuth 토큰과 계정 정보
- 활성 업데이트 저널이 참조하는 다운로드/스테이징 파일
- 새 버전의 정상 실행이 확인되지 않은 롤백 백업

정리 전에 예상 회수 용량을 계산해 UI에 표시하고, 삭제 실패는 업데이트 성공을 취소하지 않는다. 실패한 경로는 로그에 남겨 다음 시작 때 다시 정리한다.

## Error Handling and Recovery

- 다운로드 실패: 부분 파일 유지 후 재개 가능 상태로 전환
- 검증 실패: 해당 아티팩트만 삭제하고 재다운로드 제공
- 공간 부족: 필요한 다운로드/압축 해제/롤백 공간을 분리해 표시
- 활성 작업 충돌: 실패가 아니라 `작업 종료 대기` 상태로 유지
- 런타임 적용 실패: 스테이징 제거 후 기존 런타임 유지 또는 백업 복원
- 앱 설치 실패: 기존 앱을 유지하고 센터에서 재시도 제공
- 새 버전 시작 실패: 보존된 백업과 저널을 이용해 복구 안내

오류 화면은 사용자용 원인 요약, 재시도 동작, 진단 ID를 우선 표시한다. 전체 traceback은 로그/작업 상세에서만 제공한다.

## Logging

각 업데이트 로그에 다음 필드를 포함한다.

- 현재 앱 버전과 대상 버전
- 업데이트 세션 ID
- 구성요소 ID와 아티팩트 이름
- 단계 전이와 소요 시간
- 다운로드 바이트, 검증 결과, 남은 디스크 공간
- 적용 대기 원인과 활성 작업 ID
- 정리 대상/정리 결과/회수 용량
- 롤백 수행 여부와 결과

토큰, OAuth 데이터, 전체 사용자 경로 같은 민감 정보는 기록하지 않는다.

## Testing

### Unit tests

- 상태 전이와 잘못된 전이 거부
- 저널 원자 저장과 중단 상태 복원
- 매니페스트 `release_notes_url` 검증과 구형 매니페스트 fallback
- 구성요소별 재시작/유휴 정책
- 업데이트 캐시 경계 밖 삭제 거부
- 활성 저널 파일과 롤백 백업 보존
- 정리 용량 계산과 부분 삭제 실패 처리

### Integration tests

- 다운로드 중 센터 닫기/다시 열기
- 앱 재시작 후 `.part` 다운로드 재개
- 변환/학습 중 런타임 적용 대기
- 런타임 적용 성공 후 앱 계속 사용
- 앱 업데이트 재시작과 첫 실행 완료 처리
- 설치 실패 후 기존 런타임/앱 유지
- 패치노트 링크 성공/실패가 업데이트 상태에 영향을 주지 않음

### Manual release checks

- 느린 네트워크, 네트워크 단절, 디스크 부족
- NVIDIA/AMD/CPU 프로필별 런타임 업데이트
- 0.2.x와 0.3.x 설치에서 최신 버전으로 직접 업데이트
- 사용자 지정 D 드라이브 저장 구조
- 라이브러리, 모델, 출력물의 해시/개수 전후 비교

## Implementation Boundaries

- 기존 아티팩트 검증과 런타임 설치 함수는 재사용한다.
- 메인 윈도우의 업데이트 관련 분기와 작업 수명은 `UpdateCoordinator`로 이동한다.
- 업데이트 센터는 코디네이터 상태를 렌더링하고 명령만 전달한다.
- 캐시 정리는 독립 서비스로 분리해 허용된 루트 밖 경로를 받을 수 없게 한다.
- 사용자 데이터 마이그레이션과 업데이트 캐시 정리를 같은 코드 경로에서 수행하지 않는다.
